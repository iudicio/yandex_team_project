# Декомпозиция проекта на трёх участников

## 1. Роли

Backend-сервис команда не разрабатывает: он уже предоставлен. Поэтому две роли «бекенд» означают Android-разработчиков, отвечающих преимущественно за Data/Domain/Presentation.

| Код | Роль | Основная ответственность |
|---|---|---|
| `UI` | Дизайнер / Android UI-разработчик | Figma, Compose-дизайн-система, ComposeView/Composable, состояния экранов, навигация, accessibility и визуальное QA. |
| `BE-1` | Android data/domain: Search & Filters | Gradle/CI, API foundation, поиск, пагинация, отрасли, фильтры и их тесты. |
| `BE-2` | Android data/domain: Details & Favorites | Архитектурные контракты, Room, детали, избранное, офлайн и их тесты. |

Роль — основная специализация, а не жёсткий silo. У каждой фичи есть интегратор (`BE-1` или `BE-2`), UI-владелец предоставляет экран по согласованному контракту, а PR проверяет другой участник.

## 2. Правила декомпозиции

- ID и названия задач сохраняются в GitHub Issue, ветке и PR.
- Одна задача — один проверяемый результат и обычно один PR.
- Допустимые оценки: 1, 2, 3, 5 story points; более крупная работа делится.
- В Issue фиксируются `план`, `факт` и причина расхождения.
- Сначала мержатся контракты, заглушки/fake и общая инфраструктура, затем независимые реализации.
- Общая конфигурация Retrofit/OkHttp, Room, Koin и nav graph создаётся до фич, как требует официальная рекомендация.
- Пагинация поиска входит в MVP; географический фильтр и пагинация избранного — нет.

## 11. План трёх формальных итераций ревью

Порядок формальных сдач фиксирован условиями курса. Следующая review-ветка создаётся только после подготовки предыдущей; feature-PR продолжают мержиться в `develop`, но в формальную ветку попадает только разрешённый для неё scope.

| Формальная итерация | UI | BE-1 | BE-2 | Scope сдачи |
|---|---|---|---|---|
| 1 — проект и окружение | E0-01, E0-06, E0-07, E0-15 — **14 SP** | E0-02, E0-04, E0-08, E0-11, E0-12 — **12 SP** | E0-03, E0-05, E0-09, E0-10 — **11 SP** | Только Epic 0: запускаемый skeleton, темы, навигация и заглушки, API/DB/DI foundation, CI и тестовая инфраструктура. |
| 2 — основные функции | E1-05–E1-07, T-01–T-02, E2-06–E2-08, E3-07–E3-08 — **34 SP** | E1-01–E1-04, E1-08–E1-09 — **24 SP** | E2-01–E2-05, E3-01–E3-06 — **47 SP** | Поиск, экран команды, детали вакансии и избранные вакансии. Фильтров нет. |

Загрузка формальных итераций: **37 / 105 / 32 SP**. Story points отражают объём scope, а не длительность этапа; внутри второй итерации задачи можно выполнять несколькими параллельными волнами. Epic 5 остаётся stretch-backlog и не добавляется ни в одну сдачу до завершения обязательного MVP.

## 13. Definition of Ready

Задача готова к старту, когда:

- понятен пользовательский результат и указана ссылка на Figma node для UI;
- известны входы/выходы контракта и зависимости;
- есть критерии приёмки и ожидаемые error/empty/offline states;
- отсутствует незакрытое решение, меняющее архитектуру задачи;
- оценка не превышает 5 SP.

## 14. Definition of Done

Задача завершена, когда:

- выполнен её критерий, нет блокирующих TODO;
- build, detekt и затронутые тесты зелёные;
- проверены релевантные loading/content/empty/error/offline/404 states;
- UI проверен в light/dark, portrait и минимум на Android 8;
- null-поля не вызывают crash, DTO не выходят из Data;
- секреты отсутствуют в Git, fixtures, документации и логах;
- PR проверен другим участником и владельцем изменённого общего контракта;
- в Issue заполнены `факт` и причина отклонения от оценки;
- после merge выполнен короткий smoke и не обнаружена деградация.
