# Процесс разработки

## 1. GitHub Projects

Каждая строка [декомпозиции](./05-декомпозиция.md) создаётся как отдельный GitHub Issue с тем же ID.

Поля доски:

| Поле | Значения/формат |
|---|---|
| Status | Backlog → Ready → In progress → Review → QA → Done. |
| Epic | Epic 0, 1, 2, 3, 4, Stretch 5. |
| Owner | UI, BE-1, BE-2; после старта заменить реальными GitHub assignees. |
| Priority | P0 blocker, P1 MVP, P2 stretch. |
| Story points | 1, 2, 3 или 5. |
| Plan | Оценка времени участника до начала задачи. |
| Fact | Реальное активное время после завершения. |
| Iteration | 1–4. |
| PR | Ссылка на единственный основной PR. |

Рекомендуемые labels: `epic:0`…`epic:5`, `area:ui`, `area:data`, `area:domain`, `area:qa`, `priority:p0`…`p2`, `blocked`, `stretch`.

## 2. Шаблон Issue

```markdown
## Результат
Коротко: какое проверяемое изменение должно появиться.

## Scope
- [ ] Подзадача 1
- [ ] Подзадача 2

## Acceptance criteria
- [ ] Критерий из декомпозиции
- [ ] Нужные loading/content/empty/error/offline states
- [ ] Light/dark проверены, если есть UI

## Зависимости
- Depends on: #...
- Blocks: #...

## Материалы
- Figma node: ...
- ТЗ/API: ...

## Оценка
- SP: ...
- План: ...
- Факт: ...
- Причина отклонения: ...

## Проверка
- [ ] assemble
- [ ] detekt
- [ ] unit/integration tests
- [ ] manual smoke
```

## 3. Ветки

```text
main                     проверенные формальные итерации
└── develop              ежедневная интеграция команды
    ├── feature/E1-04-search-debounce
    ├── feature/E2-03-details-repository
    └── fix/E3-05-favorite-sync
```

Правила:

1. Feature/fix-ветка создаётся только от актуального `develop`.
2. Название начинается с ID задачи.
3. Один PR закрывает одну задачу и обычно не превышает 5 SP.
4. Target обычного PR — `develop`.
5. Перед review автор подтягивает `develop`, решает конфликты в своей ветке и запускает локальные проверки.
6. Прямые push в `main` и `develop` запрещены.

## 4. Формальные итерации

После согласованного инкремента:

1. От актуального `develop` создаётся `iteration_1_review` или `iteration_2_review`.
2. Открывается PR `iteration_N_review → main`.
3. Лид передаёт PR ревьюеру курса; команда продолжает новые задачи от `develop`.
4. Критические замечания исправляются в iteration-ветке.
5. После одобрения iteration-ветка мержится в `main`.
6. Затем `main` обязательно мержится обратно в `develop`, чтобы исправления не потерялись.

Внутренний план содержит четыре итерации. Для двух формальных сдач удобно объединить внутренние 1–2 в `iteration_1_review`, а 3–4 — в `iteration_2_review`.

## 5. Порядок merge

1. Контракт/domain model/navigation argument.
2. Fake/stub для параллельной работы.
3. Data/Domain implementation.
4. ViewModel и UI state.
5. XML/Fragment/adapter.
6. Интеграционные тесты и hardening.

Если contract меняется, сначала обновляется отдельным PR и получает согласие всех потребителей. Нельзя одновременно редактировать общий `nav_graph.xml`, DB schema или один DI-файл в нескольких ветках.

## 6. Pull Request

Описание PR содержит:

- Issue ID и ссылку;
- что изменено и что сознательно не входит в PR;
- способ проверки;
- результаты assemble/detekt/tests;
- light/dark screenshots для UI;
- ссылку на Figma node;
- риски, миграции и изменения контрактов;
- подтверждение, что секреты не добавлены.

### Review matrix

| Автор | Обязательный reviewer | Дополнительно |
|---|---|---|
| UI | интегратор соответствующей фичи | второй backend при изменении общего контракта. |
| BE-1 | BE-2 | UI при ресурсах, состоянии экрана или nav. |
| BE-2 | BE-1 | UI при ресурсах, состоянии экрана или nav. |

Автор не мержит PR без approval. Владелец общего файла из декомпозиции должен подтвердить его изменение.

## 7. Командная синхронизация

Короткий sync минимум раз в рабочий день:

- что завершено;
- что будет сделано дальше;
- какой blocker мешает;
- изменился ли контракт или оценка;
- нужен ли pair/review.

Blocker помечается в Issue в тот же день. Если задача превысила 5 SP фактической сложности, оставшаяся работа выносится в новый Issue, а не скрывается внутри большого PR.

## 8. Политика качества

До перевода Issue в Done:

- выполняются `assemble`, `detekt` и релевантные тесты;
- проводится ручной smoke по acceptance criteria;
- проверяются обе темы и Android 8 для UI;
- отсутствуют незакрытые критические review threads;
- проверяется отсутствие токена в diff и логах;
- после merge владелец делает smoke на `develop`.

## 9. Секреты

- Локально: игнорируемый `develop.properties`.
- CI: `GH_API_ACCESS_TOKEN`.
- В PR и Issue используется только placeholder `<token>`.
- OkHttp logging interceptor должен редактировать `Authorization`.
- При подозрении на утечку токен заменяется, а не просто удаляется из последнего коммита.
